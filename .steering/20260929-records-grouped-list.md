# 20260929 記録一覧を種類ごとにグループ表示する・食事の区分

## 要望
- 記録画面の一覧を、同じ種類の記録ごとにグループにまとめる
- グループの中は時刻順に並べる
- 食事は 朝・昼・夜・おやつ×2 の区分で記録する

## 決定事項（利用者に確認済み）
- グループ内は古い順。見出しに件数と合計を出す
- おやつは「おやつ（午前）」「おやつ（午後）」
- 同じ日・同じ区分の食事の 2 回目は上書き（体重と同じ）
- 既存の食事の記録は、時刻（日本時間）から区分を自動で割り当てる

## 方針
### 食事の区分（API・DB）
- Prisma: `enum MealSlot { BREAKFAST, MORNING_SNACK, LUNCH, AFTERNOON_SNACK, DINNER }`、`Record.mealSlot MealSlot? @map("meal_slot")`
  - 表示名: 朝食 / おやつ（午前） / 昼食 / おやつ（午後） / 夕食（並びもこの順）
- マイグレーション
  - enum と列を追加
  - 既存の MEAL を日本時間の時刻で割り当て: 〜10時 朝食、10〜11時 おやつ（午前）、11〜14時 昼食、14〜17時 おやつ（午後）、17時〜 夕食
  - CHECK 制約: MEAL なら meal_slot 必須、MEAL 以外は NULL
  - 既存データで同じ日・同じ区分が複数になる場合はそのまま残す（上書き時は最新の 1 件を更新）
- API（`POST /children/:childId/records` の MEAL）
  - `mealSlot`（必須）と `tz`（必須。体重と同じく「1日」の区切り）を追加
  - 体重の「1 日 1 件・上書き」処理を一般化し、MEAL は「こども × 日 × 区分」で 1 件にする（同じロック・同じ検索方法）
  - 応答・一覧に `mealSlot` を含める
- AI（食事の提案・週次レポート）は変更しない（時刻は今どおり渡している）

### アプリ
- 食事の入力画面に区分の選択（朝食〜夕食の 5 つ）を追加。初期値は今の時刻から上と同じ区切りで決める
- 体重と同じく、選んだ日・区分の食事が記録済みなら内容を初期値に入れ、「上書きされます」と表示（区分や日付を変えたら入れ直す）
- 一覧の行: 食事は「食事  おかゆ」ではなく「朝食  おかゆ」のように区分を出す

### 記録一覧のグループ表示（アプリ）
- グループの並びはミルク → 睡眠 → 体重 → 食事。記録のない種類は出さない
- グループ内は開始時刻の古い順。食事は区分の順（朝食 → … → 夕食）、同じ区分なら時刻順
- 見出し
  - ミルク: 「ミルク  5回 · 合計 600 ml」
  - 睡眠: 「睡眠  3回 · 合計 9時間30分」（日をまたぐ睡眠も、その日に始まった分として全時間を数える）
  - 体重: 「体重」
  - 食事: 「食事  3回」
- 各行（アイコン・要約・時刻・メモ・記録者・削除）、左右スワイプ、引っ張って更新は今のまま
- グループ分け・並べ替え・見出しの文言は画面から切り離した関数にして単体テストする

## 実装メモ（計画からの追加）
- 食事の入力画面: 区分を手で選ぶまでは、日時を変えると区分も時刻に合わせて変わる。手で選んだ後は変えない
- アプリは知らない区分の値を受け取っても一覧を表示できる（区分なし扱いで「食事」と表示）
- 1 日 1 件の処理は体重・食事で共通化し、ロックのキーを `records:daily:` に変更（体重の変更も未デプロイのため、新旧のキーが混在する期間はない）

## 検証
- マイグレーション: 使い捨ての DB（cradle_migcheck。確認後に削除）で、新しいマイグレーションの前に食事の記録を入れてから適用
  - 日本時間 0:00 / 9:59 → 朝食、10:00 / 10:59 → おやつ（午前）、11:00 / 13:59 → 昼食、14:00 / 16:59 → おやつ（午後）、17:00 / 23:59 → 夕食。ミルクは NULL のまま
  - CHECK 制約: 「ミルク + 区分あり」「食事 + 区分なし」の INSERT はどちらも拒否された
  - e2e 用 DB（cradle_test）にも適用済み。ローカル開発用 DB は以前からマイグレーション履歴が食い違っているため未適用
- API: `npm run lint`・`npm run test:e2e`（36 件）・`npm run build` 成功。`npm run test` は既存の 1 件（env.spec.ts の Gemini の既定モデル）のみ失敗（master でも失敗）
  - e2e: 5 区分をそれぞれ登録、同じ日・同じ区分の 2 回目は同じ ID を上書き、別の日は新規、同じ日の体重と食事は互いに上書きしない、mealSlot・tz なし／不正な区分は 400、食事以外に送った mealSlot は無視される
- アプリ: `flutter analyze` 問題なし、`flutter test` 全件成功
  - グループの並び・古い順・食事は区分順、見出しの件数と合計、区分の初期値の境目、知らない区分、入力画面の上書き案内と入力の保持
- API 契約テスト: e2e 用 DB につないだ API で成功（同じ日・同じ区分の食事の 2 回目が上書きされることを含む）

## レビュー結果
code-reviewer・security-reviewer とも Critical・High はなし。

### 対応したもの
- 時刻を変えても区分の初期値が追従しない → 手で選ぶまでは追従
- 未知の区分でアプリが例外になり一覧が表示できない → null 扱い
- テストの抜け（体重と食事が互いに上書きしない、手入力の保持、同じ区分の複数件の並び）
- 睡眠の見出しの式の読みやすさ
- マイグレーションの割り当ての確認（上記「検証」）
- 再レビュー（code-reviewer 2 回目）: 区分の分からない食事はグループの最後に並べる、区分の追従は食事のときだけにする

### 残るもの（対応しない・利用者判断）
- 食事の `mealSlot`・`tz` は必須。この変更より前のアプリから食事を記録すると 400 になる（ストア配布前のため許容。配布済みの版があれば、移行期間だけ省略時にサーバーが時刻から区分を決める対応が必要）
- 上書きしても記録者（createdBy）は最初に記録した人のまま（体重と同じ。「最後に更新した人」にする場合は別途対応）
- 一覧は全件を一度に組み立てる（1 日の件数は少ないため）
- 「区分を手で選ぶまで時刻に追従する」挙動のテストはない（日時の選択ダイアログの操作が必要なため見送り）
