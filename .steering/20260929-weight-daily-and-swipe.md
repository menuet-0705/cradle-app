# 20260929 体重は1日1件（2回目は上書き）・記録画面のスワイプで日付移動

## 要望
1. 体重は1日1回だけ登録できるようにし、2回目以降は既存の記録を更新する
2. 記録画面で、右スワイプで前日、左スワイプで翌日に移動する

## 方針
### 1. 体重の1日1件（API で保証する）
- 対象は **WEIGHT のみ**（ミルク・睡眠・食事は従来どおり1日に何件でも記録できる）
- 「1日」は利用者の端末のタイムゾーンで区切る（ミルクの日別集計と同じ考え方）
  - `POST /children/:childId/records` の WEIGHT に `tz`（IANA 名。例: `Asia/Tokyo`）を**必須**で追加する。検証は milk-daily の `isValidTimeZone` を使い回す
  - 既定値（UTC など）で補うと、日付の境目が黙ってずれるため必須にする。旧版アプリからの体重登録は 400 になる（MVP でストア未公開のため許容）
- 保存処理（RecordsService.create の WEIGHT 分岐）
  - トランザクション内で `pg_advisory_xact_lock(hashtext('records:weight:' || childId))` を取り、同時に2回保存されても重複しないようにする（children.service.ts と同じ方式）
  - 同じこどもで、`(started_at AT TIME ZONE tz)::date` が保存しようとしている日と同じ WEIGHT 記録を探す
    - あれば、その記録の `startedAt`・`weightG`・`note` を更新する（記録者 `createdBy` は変えない）
    - なければ新規作成
  - どちらでも、保存後の記録を返す（応答の形は変えない）
- DB のユニーク制約は付けない（「1日」がタイムゾーンで変わるため、列だけでは表せない）。そのためスキーマ変更・マイグレーションはなし
- すでに同じ日に複数ある体重の記録は、そのまま残す（上書き時は最も新しい1件を更新）

### 2. アプリ側
- NewRecord の toJson で、WEIGHT のときに端末のタイムゾーン（flutter_timezone。既に依存あり）を `tz` として送る
- 体重の入力画面
  - 選んでいる日にすでに体重があれば、その値とメモを初期値に入れ、「この日の体重は記録済みです。保存すると上書きされます」と表示する
  - 日時を別の日に変えたら、その日について同じ判定をする（その日の記録一覧 `dayRecordsProvider` を使う）
  - 上書きになる場合はタイトル・ボタンも「体重を更新」「更新する」にする
- 記録画面（RecordsTab）
  - 横方向のドラッグ（`onHorizontalDragEnd` の速度）で日付を移動する
    - 右スワイプ（指を左→右）: 前日
    - 左スワイプ（指を右→左）: 翌日（今日より先には進めない。矢印ボタンと同じ条件）
  - 一覧は縦スクロール・下タブは NavigationBar なので、横スワイプと取り合いにならない

## 実装メモ（計画からの追加）
- 体重の入力画面は、日付を変えるたびにその日の体重を入力欄へ入れ直す（記録がなければ空にする）。利用者が入力欄を触った後は入れ替えない
- 端末が `GMT+09:00` のような IANA 名でない値を返す場合は、時差から `Etc/GMT-9` を作って送る（時間単位でない時差は UTC）。ミルクの日別集計にも同じ処理を使う
- 上書きの検索範囲は ±26 時間（夏時間で 1 日が 25 時間の日を含める）。トランザクションは他と同じ `{ maxWait: 5000, timeout: 5000 }`
- 記録一覧の並びを「開始時刻が新しい順、同じなら作成が新しい順」にし、上書き対象の選び方と揃えた

## 検証
- API: `npm run lint`・`npm run test:e2e`（35 件）・`npm run build`（Vercel 用のバンドルチェック込み）がすべて成功
  - e2e で確認したこと: 同じ日の 2 回目は同じ ID の記録が上書きされる、別の日は新規、タイムゾーンで日の区切りが変わる、複数あるときは最新を上書き、夏時間の日（America/New_York 2025-11-02）、3 件同時に保存しても 1 件、`tz` なし・不正は 400、ミルクは同じ日に複数登録できる
- `npm run test` は 1 件失敗（`env.spec.ts` の Gemini の既定モデル）。master でも同じく失敗するため今回の変更とは無関係
- アプリ: `flutter analyze` 問題なし、`flutter test` 全件成功（スワイプ、体重の上書き表示、tz の送信、タイムゾーン名の補正を追加）
- API 契約テスト: API を e2e 用 DB（cradle_test）につないで起動し成功（同じ日の 2 回目の体重が上書きされ 1 件になることを確認）
  - ローカル開発用 DB はマイグレーション履歴がリポジトリと食い違っている（DB にだけ `20260928142213_ai_insights`、AI 関連 3 件が未適用）。リセットが必要でデータが消えるため触っていない
  - ローカルの環境変数ファイルの `CRON_SECRET` が起動時の検証を通らない。検証時は起動コマンドで一時的な値を渡した

## レビュー結果
code-reviewer 2 回、security-reviewer 1 回。Critical・High はなし。

### 対応したもの
- Medium: 体重の入力画面で日付を変えると、初期値と上書きの案内が噛み合わない（日付変更で購読し直し、入力欄を入れ直す）
- Medium: 端末が IANA 名でないタイムゾーンを返すと体重が保存できない（`Etc/GMT±N` に補正）
- Low: 夏時間の日に取りこぼす（±26 時間に拡大・e2e 追加）、トランザクションの待ち時間、一覧と上書き対象の並び順、読み込み中に先に入力したメモを上書きする、日付変更直後に前の日の値が残る、コメント不足、e2e のこどもの誕生日

### 残るもの（対応しない・利用者判断）
- `tz` は必須。この変更より前のアプリからの体重登録は 400 になる（ストア配布前のため許容）
- 上書きしても記録者（createdBy）は最初に記録した人のまま（計画どおり。必要なら「最後に更新した人」に変更可能）
- Node と Postgres でタイムゾーンのデータが食い違う名前は 400 ではなく 500 になる（ミルクの日別集計と同じ既存の問題）
- `assertAccess` がトランザクションの外（既存の create 全般と同じ設計）
- 体重の入力画面で日付を変える操作のウィジェットテストはない（日付ピッカーの操作が必要なため見送り）
- 読み込み中にタイトル・ボタンが「記録」→「更新」に変わる（見た目のみ）
