# 20260928 家族招待

家族（パートナー・祖父母など）を招待し、同じこどもの記録を一緒に見て・つけられるようにする。

## 前提（既存の構造）
- データは Family 単位。User は FamilyMember（OWNER / MEMBER）で家族に所属し、所属家族のこども・記録にアクセスできる
- 登録時に本人の家族が1つ作られる（OWNER）
- こども一覧・記録・集計は「所属するすべての家族」を対象に動く → 家族に参加した時点で相手のこどもが見える

## 仕様

### 招待の流れ（メール招待）
1. 招待する側: メニュー「家族」→「メールで招待」→ 相手のメールアドレスを入力して送信
2. 相手に届くメール: 招待者名・家族名と、招待リンク `https://<APP_URL>/invite#<コード>`、アプリ用の招待コード
   - コードは `#` 以降に置く（サーバーに送られず、Vercel のアクセスログに残らない）。Web は起動時に読み取って URL から消し、メモリ上に保持する
3. 招待される側:
   - Web: リンク（`/invite#<コード>`）を開く → 未ログインならログイン/新規登録 → 確認画面 →「参加する」
   - アプリ: メニュー「招待コードを入力」→ 確認 →「参加する」（モバイルのディープリンクは今回やらない）
   - リンクから来て未ログインの場合は、ログイン/新規登録のあと招待の確認画面に自動で戻る（登録時に作られた空の家族は参加時に削除）
4. 参加後はホームに相手のこどもが表示される

### 招待コードと安全性
- **招待したメールアドレスでログインしている人だけが参加できる**（コードが転送・漏えいしても第三者は使えない）。別のアドレスで登録した人は参加できないので、招待し直してもらう
- コード: 10 文字（紛らわしい文字を除いた 32 種 → 約 50 ビット）、例: `K7QM-4XP2-HN`。入力は大小文字・ハイフン無視
- DB にはハッシュ（sha256）のみ保存。平文はメール本文にだけ載せる（API の応答にも返さない）
- 有効期限 72 時間、1 回使ったら無効。取り消し可能。同じアドレスへ再送すると古い招待は取り消し
- 送信の上限（スパム踏み台対策。上限が他人の招待を妨害する手段にならないよう単位を分ける）
  - 1 家族あたり有効な招待 10 件（同じ宛先への再送は入れ替わりなので数えない）
  - 1 ユーザーあたり 1 時間 10 通 / 同じ家族から同じ宛先へ 24 時間 3 通
  - 全家族から同じ宛先へ 24 時間 10 通（既存アカウント分）。作成から 1 日以内のアカウント分は別枠で 3 通（使い捨てアカウントで既存の家族の招待を止められないように）
  - 作成から 1 日以内のアカウントが送る招待は全体で 1 日 200 通（使い捨てアカウント対策。既存アカウントは対象外。上限到達時は警告ログ）
- 参加 API はレート制限を強めにかける。無効・期限切れ・使用済み・取り消し済み・アドレス不一致は区別せず同じエラー
- メール本文の招待者名・家族名はエスケープし、テキスト中心の簡素な本文にする（なりすまし・HTML 注入対策）

### メール送信（環境差異を出さない構成）
- SMTP で送る（nodemailer）。**違いは環境変数 `SMTP_URL` / `MAIL_FROM` / `APP_URL` だけ**
  | | ローカル | 検証/本番 |
  |---|---|---|
  | SMTP | docker compose の **Mailpit**（送信メールを http://localhost:8025 で確認。外部には届かない） | **Resend** の SMTP（`smtp.resend.com`） |
  | APP_URL | `http://localhost:8080` | `https://<Vercel のドメイン>` |
- e2e テストは送信を差し替え、送られた本文からコードを取り出して参加まで確認する
- 送信失敗時は招待を作らない（エラーを返す）

### 参加時の自分の家族の扱い
- 自分の家族が「こども 0 人・自分だけ」なら削除し、招待先の家族だけに所属する（登録直後に招待を受けた人の典型ケース）
- 自分の家族にこどもがいる場合は残す（両方の家族のこどもが見える）
- 既に同じ家族のメンバーなら何もしない

### こども登録先の家族
- 複数の家族に所属している場合、登録先は「選択中のこどもの家族」（こどもがいなければ最初の家族）。API は既存の `familyId` 指定を使う

### メンバー管理（家族の画面）
- メンバー一覧（名前・役割）と有効な招待の一覧（期限・取り消し）
- 退出: MEMBER は自分で退出できる。OWNER は退出不可（最後の管理者がいなくなるため）
- メンバーの削除: OWNER のみ
- 招待の発行・取り消し: 家族のメンバー全員が可能

### 今回やらないこと
- モバイルのディープリンク（Universal Links / App Links。リンクは Web で開き、アプリではコード入力）
- 権限の細分化（閲覧のみメンバー等）、OWNER の譲渡、家族名の変更

## データモデル
```prisma
model FamilyInvite {
  id          String    @id @default(uuid()) @db.Uuid
  familyId    String    @db.Uuid
  createdById String?   @db.Uuid
  email       String    // 招待先（小文字化して保存）
  codeHash    String    @unique
  expiresAt   DateTime
  usedAt      DateTime?
  usedById    String?   @db.Uuid
  revokedAt   DateTime?
  createdAt   DateTime  @default(now())
}
```

## API（/api/v1）
| メソッド | パス | 説明 |
|---|---|---|
| GET | `/families` | 所属家族と、各家族のメンバー一覧 |
| POST | `/families/:familyId/invites` | `{ email }` 宛に招待メールを送信（コードは返さない） |
| GET | `/families/:familyId/invites` | 有効な招待一覧（宛先・期限。コードは返さない） |
| DELETE | `/families/:familyId/invites/:inviteId` | 招待の取り消し |
| POST | `/invites/preview` | コードから家族名・招待者名を確認（要ログイン、参加はしない） |
| POST | `/invites/accept` | 参加（トランザクションで使用済み化・メンバー追加・空の自分の家族を削除） |
| DELETE | `/families/:familyId/members/:userId` | メンバー削除（OWNER）／自分なら退出（MEMBER） |

- コードは URL ではなく本文で送る（アクセスログに残さない）
- エラー本文は `{ code, message }`。クライアントは `code`（ALREADY_MEMBER / TOO_MANY_PENDING / INVITE_LIMIT / INVALID_INVITE / RETRY など）で判定する
- 他家族の招待・メンバーへの操作は 404

### 反映した指摘
- (High) 参加時の空家族削除と、同時の参加・こども登録の競合 → 候補の家族行を `FOR UPDATE` でロックしてから判定し直す。デッドロック等は 1 回再試行し、だめなら 409 RETRY
- (High) 同じ宛先への同時送信で互いの招待を無効化 → 作成はアドバイザリロック内で上限確認と一緒に行い、無効化は「自分より古い招待」だけ（同一ミリ秒は ID で順序付け）
- (Medium) 外されたメンバーが自分の出した招待で戻れる → メンバー削除時にその人の招待も無効化
- (Medium) 招待コードが Web の URL・アクセスログ・履歴に残る → `/invite#<コード>` に変更し、読み取り後に URL から消す。`?invite=` の受け渡しもやめてメモリ上で保持
- (Medium) 送信上限の悪用（スパム・他人の招待の妨害）→ 上限の単位を家族・宛先・新規アカウントに分割、件名から利用者の入力を除外、名前から双方向・ゼロ幅文字を除去
- (Medium) 参加後の再読み込み失敗で「失敗」と表示される / 別アカウントでログイン中に行き詰まる → 再読み込みは失敗しても続行、「別のアカウントでログインする」を追加
- (Low) エラー判定を英語メッセージから code に変更 / メール設定の一部だけ設定は起動エラー / MAIL_FROM の形式検証 / 壊れた `#` で起動時に落ちる / 保留中のコードが残り続ける / 確認画面に「空の自分の家族は削除される」旨を表示

### 受け入れたリスク（後続で対応）
- [ ] **メールアドレスが未確認のまま登録できる**（本番公開を広げる前に対応）。招待はアドレスに紐づくが、未確認のため:
  - 招待コードが漏れた場合、そのアドレスで先に登録した第三者が参加できる（コードは本人宛てメールにしか載らず、URL にも残らないので漏れる経路は限定的）
  - 家族のメンバーは招待中の宛先アドレスが見えるので、先回りして登録すると本人が登録・参加できなくなる
  - 対応: 新規登録時のメール確認（`emailVerifiedAt`）を入れ、未確認アカウントは招待を受けられないようにする
- [ ] レート制限（IP 単位）はサーバーレスのインスタンス単位（既存の後続課題と同じ。共有ストア化で解消）
- 招待の作成は全体で 1 つのロックで直列化（現状の規模では問題なし。増えたら宛先単位のロックに）
- アカウント削除機能はまだないが、作る際はその人の招待も無効化すること
- 新規アカウント枠（全体で 1 日 200 通）を大量登録で使い切られると、登録直後の正規ユーザーも 24 時間招待できない（警告ログで検知。IP 単位の共有レート制限を入れる際に見直す）
- 生 SQL でのデッドロックの判定はエラー文字列（40P01 等）に依存。Prisma の形式が変わると 500 になる（データは壊れない）
- 招待画面にいる間にセッションが切れると、保留中のコードは破棄される（リンクを開き直せばよい）
- 複数の家族に所属していて、選択中のこどもと別の家族にこどもを登録する UI はない（登録先は選択中のこどもの家族）

- Resend のアカウント作成・送信元ドメインの認証（DNS に SPF/DKIM を追加）。未認証だと自分宛てにしか送れない
